# /feed cutover — Next → Phoenix LiveView (UI port plan 3)

Every command here runs on the box (or against it) — Neil executes. Order matters.
Rollback at any point: remove the two nginx locations and reload.

This is the first port with a **write** path. Two things make it different from the
`/sources` and `/places` cutovers:

- The write gate moves from nginx (method-based) into the app itself — a non-steward
  gets a working read-only page instead of nginx's raw 401. Step 4's browser check is
  what proves that landed.
- Migration `0010_web_write_grants_feed.sql` grants the web role `UPDATE (status)` on
  `localfinds.finds`, `INSERT` on `localfinds.feedback`, **and `SELECT (id)` on
  `localfinds.feedback`** — that last grant exists because Ecto appends
  `RETURNING "id"` to every insert against an autogenerated primary key, and Postgres
  requires `SELECT` on any column named in `RETURNING`. Without it, every feedback
  write (thumbs, star, hide — anything that inserts a `feedback` row) fails live with
  `42501 insufficient_privilege`, even though all 341 local tests pass (the test
  database runs as the owning role, which needs no grants at all).

## 0. Pre-flight (from dev)

    cd phoenix && mix test          # 341 tests, 0 failures
    npm run deploy -- --dry-run     # forwards --dry-run to gate/deploy-code/migrate;
                                     # deploy-code's rsync/git lines print $DEPLOY_HOST,
                                     # confirming this targets the localfinds box

## 1. Ship code + migration

    npm run deploy                  # gate -> code -> migrate; applies 0010
    bash scripts/deploy/deploy-api.sh

`npm run deploy` is what ships migration 0010. Without it the page renders but every
write fails with `42501 insufficient_privilege` the moment a steward clicks a button.
`deploy-api.sh` is what ships the Phoenix release — a UI-only change needs it.

## 2. Verify Phoenix serves the page before nginx points at it

    curl -sS -o /dev/null -w "%{http_code}\n" http://127.0.0.1:4000/feed        # 200
    curl -sS -X POST -o /dev/null -w "%{http_code}\n" http://127.0.0.1:4000/feed/settings
    # 403 (protect_from_forgery rejects the missing CSRF token before the
    # controller's steward check ever runs — this only proves the route exists
    # and the browser pipeline is wired up, not that the write gate works)

## 3. nginx: add BOTH locations

    sudo cp /etc/nginx/sites-available/localfinds.me \
            /etc/nginx/sites-available/localfinds.me.bak-feed-cutover

Add alongside the existing Phoenix locations:

    location = /feed {
        proxy_pass http://127.0.0.1:4000;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    location ^~ /feed/ {
        proxy_pass http://127.0.0.1:4000;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

**Both are required.** The settings form posts to `/feed/settings`; with only the exact
match, that POST goes to Next and 404s. They must also roll back together.

`X-Forwarded-Proto` is not optional: without it `force_ssl` sees http and 301s to
PHX_HOST, which a websocket cannot survive.

    sudo nginx -t && sudo systemctl reload nginx

## 4. Verify live

    curl -sS -o /dev/null -w "%{http_code}\n" https://localfinds.me/feed         # 200
    curl -sS https://localfinds.me/feed | grep -c data-phx-main                  # 1

In a browser:

- The region badge renders in the header (the data-dir canary — if it is missing,
  config reads are broken on the box).
- **Logged out**: cards, filters and pager render; **no** 👍/👎/★/Hide row on any card,
  no "Star page" / "Hide page" / "Unhide all" row, no Settings panel. This is the
  visible face of the in-app write gate that replaces nginx's method-based gate for
  this page — confirm it, don't assume it, since a missing `@steward?` check anywhere
  in the templates would only show up here, not in nginx.
- **Logged in as steward**: all of the above appear. Click 👍 or ★ on one card and
  confirm it sticks after a reload (this round-trips both new grants at once: the
  `feedback` insert with its `RETURNING "id"`, and — for ★ — the `finds.status`
  update). Save a default in the Settings panel and confirm the next visit honours it.
- The socket is connected (no full page reload when clicking a filter chip).

**If a write silently fails or the page errors on click:** the grant is the first
suspect. `Localfinds.DB.guard/1` only degrades connection-loss errors to a flash —
a permission error re-raises, so it surfaces as a crashed LiveView (the "something
went wrong, reconnecting" banner) and a stack trace in the service log:

    sudo journalctl -u localfinds-api -n 50 --no-pager | grep -i '42501\|insufficient_privilege'

Any hit means migration 0010 did not apply (or applied against the wrong database).
Re-run `npm run deploy` — the migration is idempotent — or check by hand:

    sudo -u postgres psql -d localfinds -c "
      SELECT has_table_privilege('localfinds_api','localfinds.feedback','INSERT') AS insert_ok,
             has_column_privilege('localfinds_api','localfinds.feedback','id','SELECT') AS select_id_ok,
             has_column_privilege('localfinds_api','localfinds.finds','status','UPDATE') AS update_status_ok;"

All three must be `t`.

## 5. Rollback

    sudo cp /etc/nginx/sites-available/localfinds.me.bak-feed-cutover \
            /etc/nginx/sites-available/localfinds.me
    sudo nginx -t && sudo systemctl reload nginx

The Next page and its server actions are untouched, and the `lf_settings` cookie
written by Phoenix is the same shape Next reads.
